## 1. 目标与边界

本计划处理自动工作模式在实机运行中暴露出的三类问题：

1. 常规任务、手动/附属任务与自动任务切换时的交接稳定性；
2. 农耕任务的目标扫描、路径可达性与预算饥饿；
3. 已安装附属注册的 `IMaidTask` 缺少工作可用性检测器，导致可配置但无法自动切入；
4. 缺少“能否稳定检测”的静态预检与黑白名单策略，玩家与 Agent 无法区分 NO_DETECTOR、通用 fallback 与已核验专用检测。

### 1.1 必须达成

- 自动切换只在目标任务具有**当前检测世代**下明确 `AVAILABLE` 证据时执行；
- 启用自动工作、切换/改序/删预设时：先失效旧 definitive 缓存，再 forceRescan，决策只读 fresh generation；
- 未实现专用 Detector 的附属任务不会被误判为“总是可用”，也不会被自动切入；
- 为日志已确认的高优先级任务补充专用 Detector 或明确标注为“暂不支持自动调度”；
- 提供静态兼容预检（专用 / fallback / NO_DETECTOR / 黑名单）与可手改的白名单、黑名单配置；
- 减少 `UNKNOWN`、`FULL_SCAN_ALL_UNREACHABLE`、预算耗尽造成的无效循环与切换抖动；
- 多女仆场景下保证女仆级预算公平，避免路径预算被排序靠前的 job 长期独占；
- 保持服务端权威、每女仆独立状态、真实 `maid.getTask()` 语义和手动任务保护。

### 1.2 明确不做

- 不以 `IMaidTask.isEnable(maid)` 作为通用“有工作”判断；它只表示任务可使用，不能表示环境中有目标。
- 不让未知附属任务自动切入；否则会把女仆切到无目标的工作模式。
- 不在检测阶段调用 `maid.setTask()`、`refreshBrain()`、清 Brain Memory 或修改世界。
- 不修改已完成的 `自动切换工作模式v2计划.md` 与 `独立工作检测系统重构计划.md`。
- 不要求同一 tick 内完成预设全部任务的 definitive 扫描后再决策（农耕全图扫描可跨多 tick）。
- 不把“白名单”写成“跳过可用性检测、直接当永远可切”；白名单仅排除未兼容提醒并标记信任，运行时仍要求当前 generation 的 `AVAILABLE` 证据。

## 2. 当前实现基线

```text
AutoWorkState(enabled + presetId)
        ↓
AutoWorkPreset(order)
        ↓
TaskDetectionScheduler ──> MaidDetectionCache
        ↓
TaskSwitchDecisionEngine.switchTo(...)
        ↓
AutoWorkInternalSetTaskGuard.runInternal(maid.setTask)
        ↓
TLM EntityMaid.setTask() -> refreshBrain(ServerLevel)
```

### 2.1 已确认正确的交接契约

- `TaskSwitchDecisionEngine.switchTo()` 是自动调度唯一调用 `maid.setTask()` 的位置；
- 网络包、GUI、Agent Tool 只修改自动状态/预设，并请求调度器评估，不直接切真实任务；
- TLM `EntityMaid.setTask(IMaidTask)` 在服务端会调用 `refreshBrain()`；
- `AutoWorkInternalSetTaskGuard` 标记内部切换，外部 `setTask()` 不会直接清空自动工作状态；
- `EXTERNAL_UNKNOWN_CURRENT` 会保留未知的当前真实任务，防止自动系统抢走附属或代码手动设置的工作；
- 手动点击 TLM 原始工作按钮：`AbstractMaidContainerGuiMixin` 已先发 `SetMaidAutoWork(false)`。

### 2.2 当前立即评估与缓存的限制

`TaskAutoSwitchHandler.requestImmediateEvaluation(maid, reason)` **已经保存 reason**，并能绕过 `PollInterval`。  
真正的缺口是：

1. **不失效** `MaidDetectionCache` 中旧 definitive 结果；
2. **不强制** 新预设任务立即重扫；
3. 新旧预设 **UID 重叠**（如都含 `grass` / `attack`）时，可能复用旧 generation 的 `AVAILABLE`。

因此 A1 的修正目标是：  
**失效 stale definitive → forceRescan → 决策只消费当前 generation 的 fresh 结果**；  
而不是“补存 reason”，也不是“等全部任务 definitive 才允许决策”。

### 2.3 当前预算与调度事实

| 项 | 现状 |
|---|---|
| 全局块预算 | `DetectionBlockBudgetPerTick` 默认 **256** |
| 全局路径预算 | `PathCheckBudgetPerTick` 默认 **4** |
| 单 farm detector 块上限 | 硬编码 `PER_FARM_DETECTOR_BLOCK_BUDGET = 64` |
| Job 排序 | 全体 `IAttackTask` → 当前任务 → `priorityIndex` |
| 轮转 | **job 级** round-robin（`roundRobinStart`），**非**女仆级预算配额 |
| 无 Detector 任务 | 仍进入 `DetectionJob` 列表并占 RR 槽位；返回 `NO_DETECTOR` |
| 农耕 evidence | 已区分 `FULL_SCAN_EMPTY` / `FULL_SCAN_ALL_UNREACHABLE` / `BLOCK_BUDGET_EXHAUSTED` / `PATH_BUDGET_EXHAUSTED` |
| 服务绑定 | `ServerStarting` / `ServerStopped`；**不是** datapack `/reload` |

A2 的重点是从 job 级 RR 升级为 **女仆级预算配额**，并补统计；不是从零发明 evidence 分类。

## 4. 阶段 A：检测与交接稳定性

### A1. 检测世代、缓存失效与 forceRescan

**问题**：立即评估已绕过轮询并带 reason，但可能消费旧预设遗留的 definitive `AVAILABLE`（尤其 UID 重叠时）。

**实现**：

1. 在每女仆 runtime 状态中增加 `detectionGeneration`（或 `presetSignature = presetId + order hash`）；
2. 扩展立即评估请求为 `{ reason, forceRescan, generation }`（reason 已存在，增量字段即可）；
3. 以下操作必须对该女仆 **bump generation + 失效 definitive cache（及可选 cursor）+ forceRescan**：
   - 启用自动工作（`SetMaidAutoWork(true)` / Agent enable）；
   - 切换预设（`SetMaidAutoWorkPreset` / Agent select）；
   - 创建并绑定新预设；
   - 当前预设内增删/改序任务（`Add/Remove/MovePresetTask`，仅当女仆正在使用该预设）；
   - 删除预设后回退默认（`DeletePreset` + `reassignLoadedMaidsToDefault` 之后）；
4. `TaskDetectionScheduler` 对本 tick 的 `forceRescan` 女仆优先分配检测机会；
5. **决策规则（修订）**：
   - 禁止读取 stale generation 的 definitive 结果；
   - **允许**在高优先级任务已有当前 generation 的 fresh definitive 时决策；
   - 候选任务仍为扫描中 `UNKNOWN` 时保持不切（与现有 `findHighestAvailable` 一致）；
   - **不要求**同 tick 扫完预设内全部任务；
6. 日志增加 `generation`、`presetId`、`reason`、`freshTaskCount`、`staleIgnoredCount`。

**验收**：

- 新旧预设 UID 重叠时切换：首条有效 `TaskDecision` 不引用旧 generation 缓存；
- 删预设回退默认后：受影响且已启用的女仆会 forceRescan 并重新评估。

### A2. 预算公平性与扫描完成度

**问题**：已有 **job 级** round-robin，但 job 排序为「全体 attack → 当前任务 → priorityIndex」，在 `PathCheckBudgetPerTick=4` 下，路径预算常被排序靠前的 farm/attack job 吃光；多女仆时表现为部分任务长期 `PATH_BUDGET_EXHAUSTED` / `BLOCK_BUDGET_EXHAUSTED`。

**实现**：

1. 每 tick 输出：启用女仆数、due job 数、块/路径预算消耗、预算耗尽次数、forceRescan 女仆数；
2. 引入 **女仆级预算配额**（每女仆 path/block cap 或女仆轮转桶），避免“排序靠前的女仆/任务”持续独占全局 path=4；
3. 评估是否弱化“全局 attack 绝对优先占满 path 预算”对 farm 扫描的饿死效应（攻击检测本身几乎不吃 path，但排序会把其后 farm 挤到 path 已耗尽区间）；
4. 无 Detector（`isUnknown`）的任务：**不进入**消耗 block/path 的检测循环，仅限流 WARN（仍永不自动切入）；
5. 为 `TaskScanCursor` 或 cache 侧记录完整扫描周期数与连续预算耗尽次数；超过阈值时降低该任务本轮调度权重并让出预算；
6. 调默认预算前必须先有基准日志；同时核算硬编码 `PER_FARM_DETECTOR_BLOCK_BUDGET=64` 与全局 256 的关系；
7. 保持 detector 内已有的 evidence 四分法，调度/决策侧不得把四者混成单一不可用。

**验收**：两只以上女仆、各配置多个农耕任务时，每只女仆的每个 farm 任务都能在有限 tick 内完成至少一轮完整扫描；日志不再由单一女仆的 `PATH_BUDGET_EXHAUSTED` 长期主导。

### A3. 防抖与真实工作验证

**问题**：日志出现 `attack ↔ grass`、`danmaku_attack ↔ compat_melon` 周期性来回切换。  
现状：`MINIMUM_TASK_HOLD_TICKS` 默认 60；`AVAILABLE_CONFIRMATIONS` 默认 **1**（单次 AVAILABLE 即可切）；`MaidSwitchState` 尚无反向切换计数。约 60 tick 往返可能是 hold 边界上的“合法切换”被放大，而非完全无保护。

**实现**：

1. 在 `MaidSwitchState` 记录上一任务 UID、切换理由、目标位置/实体、连续反向切换次数与冷却截止 tick；
2. 同一任务对在短窗口内反向切换达阈值 → 进入有限反抖冷却 + 限流 WARN；
3. 反抖仅约束“可推迟的普通切换”；**明确与 `ExperimentalAttackPreempt` 的交互**：
   - preempt 默认关闭；开启时是否计入反向对、是否共用冷却，必须在配置注释与日志中写清；
   - 不得因 `UNKNOWN` 强制切换（保持现有决策契约）；
4. `TaskStartup` / handoff 日志补充：切换前后 UID、presetId、排名、evidence、目标、Brain mask、generation；
5. 保留 `ForceBrainRefreshOnStuck`，但刷新前必须确认：当前 generation 下任务仍 `AVAILABLE`，且存在最近可达目标证据；避免把扫描不足误诊为 Brain 卡死。

**验收**：攻击目标频繁出现/消失时，切换次数不超过 hold + 反抖配置允许范围；同一任务对不会在默认配置下每 60 tick 无限往返。

## 5. 阶段 B：专用 Detector 兼容层

### B1. 兼容层结构

新增 `priority/detection/compat/`，每个 Detector 独立文件，不在通用检测器中加入附属反射逻辑：

```text
compat/
  BuiltinShearsDetector.java
  MaidUsefulTreeDetector.java
  MaidSoulKitchenBerryDetector.java
  MaidStorageManagerDetector.java
  BoardGamesDetector.java                 # 仅在可定义可靠条件后实现
  FeedAnimalDetector.java                 # 覆盖错误 IAttackTask fallback
  CompatDetectorBootstrap.java
```

注册必须满足：

- 只在对应 Mod 已加载时注册；
- UID 注册优先于 `IAttackTask` / `IFarmTask` fallback（`TaskWorkDetectorRegistry` 已支持）；
- 缺少目标 Mod 的类时不得 ClassLoad；
- Detector 仅读取实体、方块、背包和公开 API；
- 返回 `AVAILABLE` 时必须给出 evidence 和目标位置/实体 UUID；
- API 无法可靠判断时保守返回 `UNKNOWN` 或 `UNAVAILABLE`，不得猜测可用。

### B2. 任务实施顺序

| 优先级 | Detector | 预研要求 | `AVAILABLE` 条件 | 备注 |
|---|---|---|---|---|
| P0 | `MaidUsefulTreeDetector` | 核验 `MaidTreeTask` 的公开过滤、范围、原木标签 | 范围内存在任务认可且可达的原木 | 不能仅见到任意原木就判定可砍 |
| P0 | `MaidSoulKitchenBerryDetector` | 核验 `ICompatFarmTask`、目标方块表、收获规则 | 存在可收获且可达的浆果/果树目标 | 不直接依赖 MSK 私有类；优先公开 API |
| P1 | `BuiltinShearsDetector` | 核验 TLM 剪毛任务对目标羊、冷却、羊毛状态和范围的规则 | 存在可剪且可达的羊 | 返回目标羊 UUID |
| P1 | `MaidStorageManagerDetector` | 核验 Storage Manager 公开能力/仓库标记/待整理条件 | 附近可访问仓储确有待整理项 | 若没有稳定公开 API，先保持不支持 |
| P2 | `BoardGamesDetector` | 明确玩家、棋盘、距离、背包等完整发起条件 | 所有交互前置条件均满足 | 未能可靠定义前，不注册 Detector |
| P2 | `FeedAnimalDetector` | 核验 TLM/MSK 喂动物语义 | 存在可喂动物且背包有有效食物 | 覆盖错误的 `IAttackTask` fallback |

### B3. UI、Tool 与 Context 提示

现状：`MaidAutoWorkContext` / GUI / `auto_work` Tool **均无** detector 覆盖提示；`isUnknown()` 仅调度器 WARN 使用。

1. GUI 可用任务列表中，对无 Detector 的任务显示“不可自动检测”状态/Tooltip；
2. Agent `auto_work.query` 的任务条目附带检测器状态；
3. `MaidAutoWorkContext` 用文字说明当前预设包含的未检测任务；
4. WARN 使用每任务、每女仆、每个冷却窗口限流，避免日志刷屏；
5. 预设保存/编辑时做一次静态检测器覆盖检查，给出一次明确提示。

**验收**：用户在预设中加入 `maid_tree` 或 `berries_farm` 时，若兼容已实现则能拿到正确目标证据并切换；若未实现则 GUI/Tool/日志均明确说明原因。

## 6. 阶段 B0：静态兼容预检与黑白名单

**定位**：把“能否稳定检测工作可用性”提升为一等公民。  
与运行时可用性检测（A/B 的 `AVAILABLE`）分层：本阶段只回答 **“这个任务有没有可靠检测来源、是否被策略禁止”**，不扫世界、不 `setTask`。

**实施策略**：以开发/测试为主，先做分类器与空配置占位，**不**追求完整用户体验；排序屏蔽等后续完善。

### B0.1 静态兼容分类器

在服务器侧对 `TaskManager` 已注册任务做一次静态扫描（进服后一次，或配置/任务表变更后重算）：

1. 调用 `TaskWorkDetectorRegistry.resolve(task)` 判定来源：
   - 专用 UID Detector；
   - `IAttackTask` / `IFarmTask` fallback；
   - `NO_DETECTOR`；
2. 叠加黑白名单与内置“已知问题表”（如错误 fallback：`feed_animal_t` → 攻击）；
3. 输出 `TaskCompatReport`（内存结构 + 可选 JSON 快照）：`uid`、`来源 mod`、`等级`、`原因`、`是否允许自动调度`；
4. 启动校验：名单里的 UID 未注册或拼写错误时 WARN 提示，不中断加载。

### B0.2 兼容等级

| 等级 | 含义 | 默认自动调度 |
|---|---|---|
| `SUPPORTED` | 专用 Detector，语义已核验 | 允许 |
| `FALLBACK` | 仅接口 fallback（farm/attack） | 允许，但标记“通用检测，语义可能不精确” |
| `UNSUPPORTED` | `NO_DETECTOR` 或明确无法可靠判断 | 禁止自动切入 |
| `BLOCKED` | 黑名单强制禁止 | 禁止自动切入 |

- **白名单** = 开发者/玩家确认可信的 UID；排除“未兼容提醒”，运行时仍需 `AVAILABLE`。
- **黑名单** = 明确未实现或检测不稳定；优先级最高，覆盖白名单与 fallback。
- 优先级：`黑名单 > 白名单 > 自动推断`。
- 白名单写了但实际 `NO_DETECTOR`：WARN 并降级为不可调度，防止配置错误假装可检。

### B0.3 黑白名单配置（占位优先）

- 新增独立配置文件（建议 `config/tlm_sincerely/auto_work_compat.json`，先不入 ForgeSpec 以方便手改）；
- 首期提供**空配置占位**：`blacklist = []`、`whitelist = []`、`knownBadFallback = []`、默认策略枚举；

### B0.4 聊天提醒（进服）

- 时机：玩家登录后短延迟一次性推送；
- 内容摘要：黑名单任务、静态判定为 `UNSUPPORTED` 且未加白的任务、可疑错误 fallback、部分支持任务（如 cook 仅 furnace）；只列条数 + 前 N 个 UID，详情进日志；
- 权限级别：可配置推送目标（如 `ALL` / `OP_ONLY` / `DISABLED`），**可通过命令配置**（见 B0.6），并写入配置持久化；

### B0.6 命令管理

## 8. 多女仆并发压力分析（单人 / 专用服）

> 本节描述**当前实现**的压力特征，作为 A2 调参与验收的依据；不引入第二线程做检测。

### 7.1 执行模型

- 全部检测与决策在 **服务端主线程** `TickEvent.ServerTickEvent` END 相位同步执行；
- 单人（集成服）与专用服 **算法相同**；差异主要在：主线程是否还要渲染/客户端逻辑（单人同进程）、实体总数、区块加载范围、MSPT 余量；
- 过滤条件：`Activity.WORK` **且** `AutoWorkState.enabled`；未启用自动工作的女仆不进 scheduler；
- 每 tick 额外成本：`findWorkingMaids` 遍历 `server.getAllLevels()` 全部实体做类型判断（与启用数无关的固定扫描开销）。

### 7.2 每 tick 成本构成

| 阶段 | 复杂度（近似） | 主要开销 |
|---|---|---|
| 收集 WORK 女仆 | O(全服实体) | 实体遍历 |
| 解析 preset / 建 job | O(启用女仆 × 预设任务数) | 轻量 |
| Detector 执行 | 受 **全局** block=256、path=4 硬顶 | 方块读取、`canHarvest`/`canPlant`、`canPathReach` |
| 决策 | O(启用女仆 × 任务数) | cache 读、偶发 `setTask`+`refreshBrain` |
| Startup trace | 每已切换女仆至多 120 tick | Brain memory 查询 |

**瓶颈几乎总是路径可达性**：默认全服每 tick 最多 **4 次** `canPathReach`。  
块扫描默认 256，且单 farm job 再 cap 到 64，相对宽松。

### 7.3 负载粗算（默认配置）

设：

- \(M\) = 启用自动工作且处于 WORK 的女仆数  
- \(T_f\) = 每女仆预设中的 farm 类任务数（吃 block/path）  
- \(T_a\) = 攻击类任务数（几乎不吃 path，interval 5–10 tick）  
- 全局 path 预算 \(P=4\)，block 预算 \(B=256\)

则：

- 同时 due 的 farm job 上限约 \(M \times T_f\)（再受 minInterval / cursor 是否未完成影响）；
- **路径维度**：全服每 tick 最多推进 4 次可达性检查。若某 tick 有 \(K\) 个 farm job 都急需 path，则平均每个 job 约 \(4/K\) 次；\(K=8\) 时约 0.5 次/job/tick；
- **完整一圈农耕扫描**：范围由 home/restrict 半径决定，格子数近似 \(O(R^2 \times V)\)（\(V\) 为垂直层）。在 path 饥饿时，扫描完成时间近似随 \(M \times T_f\) **线性变差**；
- **攻击检测**：`IAttackTask.findFirstValidAttackTarget`，不走 path 预算，但多女仆时仍占主线程 CPU；通常远小于 pathfinding；
- **`setTask`/`refreshBrain`**：切换瞬间尖峰；多女仆同时切换（例如共同遭遇敌对生物）会叠加 Brain 重建成本。

### 7.4 场景压力等级（经验表）

| 场景 | 约略规模 | 压力 | 表现 |
|---|---|---|---|
| 单人 1 女仆 × 2–4 farm | \(M=1, T_f\le4\) | 低 | 数 tick～数十 tick 内可 definitive |
| 单人 4 女仆 × 4 farm | \(M=4, T_f=4\) → 16 farm job | 中 | path=4 下完成度明显变慢；易见 `PATH_BUDGET_EXHAUSTED` |
| 单人 8+ 女仆 × 多 farm + 攻击 | \(M\ge8\) | 中高 | 扫描 UNKNOWN 拉长；决策更依赖旧 definitive（A1 前有风险） |
| 专用服 16 女仆分散加载 | 视活跃区块 | 高 | 主线程 MSPT 与 pathfinding 争用；未加载区女仆不在 `getAllEntities` 则不参与 |
| 专用服 30+ 启用自动工作 | \(M\ge30\) | 很高 | path 预算近乎轮询饥饿；需女仆级配额 + 可能上调 path 或降 farm 密度 |
| 大量 NO_DETECTOR 任务进预设 | 任意 | 空转/日志 | 现占 RR 槽；A2 后应跳过检测循环 |

### 7.5 单人 vs 专用服差异

| 维度 | 单人（集成服） | 专用服 |
|---|---|---|
| 调度代码路径 | 相同 | 相同 |
| 主线程竞争 | 与客户端渲染/集成逻辑同进程，MSPT 更敏感 | 纯服务端，通常更稳，但实体/玩家更多 |
| 区块加载 | 跟随本地玩家 | 多玩家加载圈叠加，活跃女仆可能更多 |
| 网络 | 本地 | C2S/S2C 与 Agent 仅改状态，检测仍在服主线程；**不**把检测分到客户端 |
| 风险形态 | 卡顿体感（掉帧/卡 tick） | MSPT 上涨、全服逻辑变慢 |
| A2 目标 | 相同公平算法 | 相同；调参可按服规提高 path 预算 |

**结论**：不存在“服务器更重、单人更轻”的算法分叉；压力由 **启用自动工作的 WORK 女仆数 × 吃预算的任务数 × 扫描半径** 决定。单人往往先感到卡顿，专用服则体现为 MSPT 与全服延迟。A2 的女仆级配额对两者同等必要。

### 7.6 A2 落地后的压力治理目标

1. 任意启用女仆在预算耗尽时仍能在有限 tick 内分到 path/block（公平性 > 单女仆最快完成）；
2. 默认 path=4 下，**8 女仆 × 4 farm** 仍应能在可配置的时限内完成每任务至少一轮扫描（具体 tick 数由 A2 基准日志标定）；
3. 上调预算必须对照 MSPT：优先女仆级公平，其次小幅提高 `PathCheckBudgetPerTick`，避免单 tick pathfinding 尖峰；
4. 诊断日志需能回答：本 tick 多少女仆在抢 path、谁被饿死、完整扫描周期多久。

统一前缀并保留女仆 UUID、preset UUID、task UID：

|---|---|
