## 4. 已确认的架构决策

### 4.1 自动工作模式不是工作任务

v2 **不注册** `AutoSwitchTask implements IMaidTask`，也不让一个虚拟任务代理攻击、农耕等真实任务的 Brain 行为。

原因：主模组及其他附属会通过 `maid.getTask()`、任务 UID、任务类型、Brain Tasks 和任务配置数据识别当前工作。让女仆表面上保持虚拟任务、实际执行其他任务，需要代理所有这些行为，兼容面不可控。

改为将自动工作模式建模为独立调度状态：

```text
AutoWorkState（本模组状态）
  enabled          是否由自动调度器管理
  presetId         所选工作顺序预设的稳定 UUID
  revision         用于客户端快照失效判断

maid.getTask()（主模组真实状态）
  当前实际执行的攻击、农耕、采集等 IMaidTask
```

自动调度器仍可调用 `maid.setTask(realTask)`，但**不得**更改 `AutoWorkState.enabled`。因此真实任务发生自动变动不会退出自动工作模式，也不会让任务模式页面丢失排序配置入口。

### 4.2 每女仆持久化与运行时状态

`AutoWorkState` 是每只女仆的持久化状态，优先使用 TLM 提供的 `TaskDataRegister` / `ILittleMaid.registerTaskData` 扩展机制；只有确认无法满足持久化和同步需求时，才使用带命名空间的实体 PersistentData：

```text
tlm_sincerely:auto_work_enabled : boolean
tlm_sincerely:auto_work_preset  : UUID
```

运行时的 `lastSwitchTick`、检测缓存、外部改动宽限时间和 Brain 启动跟踪继续置于 `TaskDetectionRuntimeState`，不写入存档。

`TaskAutoSwitchHandler` 的筛选条件改为：

```java
maid.getScheduleDetail() == Activity.WORK
    && AutoWorkStateService.isEnabled(maid)
    && PriorityConfig.ENABLED.get();
```

不再通过当前任务 UID 判断是否由自动调度器管理。

### 4.3 用户操作与外部兼容规则

| 事件来源 | `AutoWorkState` 行为 | 真实任务行为 |
|----------|---------------------|--------------|
| 点击“自动切换工作”虚拟条目 | 启用；若无预设则绑定默认预设 | 保留当前任务，下一次检测后按顺序切换 |
| 再次点击虚拟条目 | 关闭 | 保留当前任务 |
| 玩家选择普通工作模式 | 关闭，表示玩家手动接管 | 正常交由主模组切换 |
| 本模组决策引擎 | 保持启用 | 调用 `maid.setTask(realTask)` |
| 其他附属改动真实任务 | 保持启用 | 记录 60-100 tick 宽限，避免互相抢占 |
| 全局配置关闭 | 保持启用但暂停调度 | 保留当前任务，绝不强制变为空闲 |

外部改动的识别必须在 `maid.setTask()` 路径上记录“本模组内部切换”标志。非内部来源的连续改动应延长宽限或暂时挂起该女仆的自动调度，并以限频日志提示兼容冲突。

## 5. 服务端权威的预设与同步模型

### 5.1 预设库与每女仆选择

预设定义由服务器共享，但不再维护全局 `activePresetName`。每只启用自动工作模式的女仆通过 `presetId` 指向一个预设：

```text
服务器预设库
  日常工作（UUID-A）
  战斗巡逻（UUID-B）

女仆甲 -> UUID-A
女仆乙 -> UUID-B
```

预设 ID 必须为 UUID，名称仅用于展示和重命名。删除正在使用的预设时，服务端应先将所有引用该 ID 的女仆回退到 `defaultPresetId`；若被删除的是默认预设，则拒绝操作或先创建新的默认预设。

### 5.2 数据模型与 JSON v3

`TaskPriorityPreset` 仅保存名称、稳定 UUID 和 `order`。列表位置即优先级，索引 0 最高：

```java
public final class TaskPriorityPreset {
    private final UUID id;
    private String name;
    private final List<ResourceLocation> order;

    public boolean hasTask(ResourceLocation taskId) { return order.contains(taskId); }
    public void addTask(ResourceLocation taskId) { /* absent 时追加 */ }
    public void removeTask(ResourceLocation taskId) { /* 删除 */ }
    public void moveTask(ResourceLocation taskId, int targetIndex) { /* 夹紧后移动 */ }
}
```

新文件格式：

```json
{
  "version": 3,
  "defaultPreset": "9f5a2c3e-0000-0000-0000-000000000001",
  "presets": [
    {
      "id": "9f5a2c3e-0000-0000-0000-000000000001",
      "name": "默认预设",
      "order": ["touhou_little_maid:attack", "touhou_little_maid:farm"]
    }
  ]
}
```

### 5.3 迁移与文件可靠性

| 来源版本 | 迁移规则 |
|----------|----------|
| 无 `version` / v1 | 根据 `priorities` 数字升序展开；同数字遵循旧 `order`；只在 `priorities` 中的任务也必须保留；仅在 `order` 中的任务追加到末尾 |
| v2 | 保留纯 `order`，为每个预设生成 UUID；旧 `active` 映射为 `defaultPreset` |
| v3 | 直接读取并校验 UUID 唯一、名称非空、任务 ID 合法 |

迁移前复制原文件为 `task_priority_presets.json.v<old>.bak.<timestamp>`。写入使用同目录临时文件和 `Files.move(..., ATOMIC_MOVE, REPLACE_EXISTING)`；无法原子移动时记录警告后安全替换。解析失败时不覆盖原文件，重命名为 `.broken.<timestamp>` 并创建新的默认库。

预设状态必须由服务器线程管理。将原有静态 `TaskPriorityManager` 改为按 `MinecraftServer` 生命周期创建的 `TaskPriorityService` 或挂载到 `TaskDetectionRuntimeState` 的服务；保持 `LinkedHashMap` 插入顺序，不使用 `ConcurrentHashMap`。所有读写和文件 I/O 都在服务器线程串行执行。

### 5.4 网络协议

客户端 GUI 不得再直接调用 `TaskPriorityManager.loadPresets()` 或写入 `FMLPaths.CONFIGDIR`。新增服务端权威网络层：

| C2S 请求 | 服务端校验与效果 |
|----------|------------------|
| `RequestAutoWorkSnapshot` | 返回可见女仆状态、预设库与版本号 |
| `SetMaidAutoWork` | 校验玩家能操作该女仆，启用或关闭状态 |
| `SetMaidAutoWorkPreset` | 校验预设存在且玩家有操作权限 |
| `Create/Rename/DeletePreset` | 校验名称、引用关系与权限后原子保存 |
| `Add/Remove/MovePresetTask` | 校验任务存在、去重和目标索引后原子保存 |

每次成功写操作向请求者及相关观察者发送 S2C 快照或增量。所有 packet handler 使用 `context.enqueueWork` 切回服务器/客户端主线程。v2 的预设库权限默认沿用女仆操作权限；若无法获得可靠权限 API，则仅允许女仆所有者和 OP 修改。

## 6. 界面重构

### 6.1 虚拟“自动切换工作”条目

在主模组左侧工作模式选择栏注入一个**纯 GUI 控制条目**，而非加入 `TaskManager`：

```text
自动切换工作
现在女仆能根据周围情况自动切换工作模式了
在右侧任务模式中配置工作模式与优先级
```

条目的状态：

| 状态 | 渲染 |
|------|------|
| 当前女仆未启用 | 标准任务列表样式 |
| 当前女仆已启用且全局开启 | 主模组任务选中蓝色样式；实际任务另以小标记表示“当前执行” |
| 当前女仆已启用或用户悬停，且全局关闭 | 红色文字/红色高亮；仍允许点击启用或关闭 |

点击普通任务条目前，Mixin 必须先发送 `SetMaidAutoWork(false)`，再调用原始主模组点击逻辑，确保“手动选择即退出自动模式”。点击虚拟条目只发送状态包，不调用 `maid.setTask()`。

`TaskButtonMixin` 仅处理显示和点击桥接，且对 `renderWidget` 保持 `remap = true`。在实现前必须以最小 Mixin smoke test 验证 TLM 1.5.3 的实际任务列表渲染路径。

### 6.2 任务模式 Tab 的工作自切换配置

自动模式启用时，任务模式 Tab 默认显示工作自切换配置；同时必须提供“当前任务配置”入口，避免玩家无法编辑攻击目标等原生任务配置：

```text
[自动工作顺序] [当前任务配置]

自动工作顺序：预设选择、可选工作模式、已配置顺序
当前任务配置：主模组当前真实任务原有的配置页面
```

排序区域不显示数字优先级。左栏添加任务，右栏通过上移、下移和移除操作排序；两栏滚轮均只滚动列表。

任务模式 Tab 为容器化 GUI，不能假设存在 `IMaidTask.getTaskConfigGui()`。实施前必须完成 GUI API Spike：

1. 核验 `IMaidTask.getTaskConfigGuiProvider(EntityMaid)`、`TaskConfigContainer`、`MenuType` 注册和 `RegisterMenuScreensEvent` 的附属扩展路径。
2. 若扩展路径可行，实现自定义 `MenuProvider`、`TaskConfigContainer` 和 `MaidTaskConfigGui`。
3. 若不可行，使用最小 Mixin 在既有任务模式右侧内容区域注入独立组件；只在该路径无法保持主模组页面时保留 SideTab 独立 Screen 作为临时回退。

API Spike 的证据和选定路径必须先写入 `DEVELOPMENT.md`，再开始界面正式实现。

### 6.3 全局配置

`PriorityConfig.ENABLED` 改为默认 `true`，翻译改为“启用自动工作模式”。它只控制调度器是否运行，不修改任何女仆的 `AutoWorkState`，也不改变当前真实任务。

工作自切换页面显示只读状态标签：

```text
自动工作模式：开
自动工作模式已在模组配置中关闭
```

第二种状态使用红色，并提供跳转主模组配置页的按钮或明确提示，不再在排序页面直接改 Forge 全局配置。

### 6.4 A1 验证后的确定实现路径（2026-08-09 修订）

第一版 Spike 曾选择在 `MaidTaskConfigGui` 右侧叠加排序控件，但实机验证表明该方案会与当前真实任务配置竞争、产生点击透传，并且 `getXSize()` 不是任务配置内容宽度。经修订，v2 使用独立的 `MenuType`、`TaskConfigContainer` 和 `AbstractMaidContainerGui`，使自动工作配置不再附着或干扰真实工作模式。

已确定的实现路径：

| 目标 | 实现 |
|------|------|
| 自动工作开关 | `MaidContainerGuiEvent.Init` 在女仆立绘下方追加 `AutoWorkVirtualTaskButton`；尺寸固定 76×19，避开工作列表、分页和任务配置区域 |
| 虚拟条目点击 | 仅发送 `SetMaidAutoWorkC2SPacket`，不调用 `maid.setTask()` |
| 玩家选普通任务 | `taskButtonPressed(IMaidTask, boolean)` 的 HEAD 注入先发送关闭自动状态包，再执行主模组原有任务切换 |
| 自动排序页面 | `MaidTabs#getTabs` RETURN Mixin 追加第 4 个顶部 Tab；点击后发 `OpenAutoWorkConfigC2SPacket`，服务端 `NetworkHooks.openScreen` 打开独立菜单 |
| 独立菜单 | `AutoWorkConfigContainer extends TaskConfigContainer` + `AutoWorkConfigScreen extends AbstractMaidContainerGui`；在 TLM 原生框架内只绘制右侧 176×137 配置区 |
| 原生配置保留 | 自动工作屏与攻击、农耕等真实任务配置屏完全分离；切换回原任务配置 Tab 后无自动工作控件残留 |
| 客户端数据 | 仅读取 `ClientAutoWorkService` 的 S2C 快照并发 C2S 操作包；不读写 JSON |
| 样式与输入 | 配置控件使用 TLM `maid_gui_task.png` 的棕色底与不透明黑字；控件经 `addRenderableWidget` 注册，不发生点击透传 |
| 旧入口 | 删除旧 `TaskPriorityScreen`、SideTab 与任务配置浮层，防止继续写入旧 JSON 或覆盖真实任务页面 |

TLM 自定义成员（`MaidTabs#getTabs`、`taskButtonPressed`）的注入使用 `remap = false`。独立 Screen 不能继承 `MaidTaskConfigGui`，否则 TLM 会同时高亮“任务配置”与自动工作 Tab；应继承 `AbstractMaidContainerGui`。

## A.1 配置 bug 修复（旧草案）

### 4.1 问题诊断

**`TaskPriorityManager`** 当前实现的已知问题：

1. **`loaded` 标志位全局单一**：`loadPresets()` 使用 `static boolean loaded` 防止重复加载，但在单人→退出→重进时不会重置。解决方案：在 `ServerStopped` 事件中调用 `reset()` 方法清空 `presets` Map 并重置 `loaded = false`。

2. **切换预设时的编辑状态不同步**：`TaskPriorityScreen.switchPreset()` 更新 `editingPreset` 引用指向新预设后调用 `setActivePreset(name)` → `savePresets()`，但若玩家正在 `presetNameField` 中编辑名称未提交就切换，旧预设名不会被保存。解决方案：在 `switchPreset()` 前先执行 `commitPresetName()`。

3. **新建预设时的名称冲突**：`newPreset()` 使用 `"预设 " + (size + 1)` 生成名称，如果玩家删除中间预设后重新创建，可能与已有预设同名导致 `LinkedHashMap.put()` 覆盖。解决方案：生成名称时检查是否已存在，若存在则递增后缀。

4. **多女仆全局预设的一致性**：当前预设为全局单例（`static Map<String, TaskPriorityPreset> presets`），所有女仆共用。这在设计上是有意的（所有女仆共享一套工作排序），但需要确认：
   - 决策引擎 `TaskSwitchDecisionEngine` 读取预设时无需同步（单线程服务端主线程）✓
   - GUI 界面操作（客户端线程）修改预设后通过 `savePresets()` 写入磁盘，但服务端不会自动重新加载。解决方案：在 `savePresets()` 后触发 `loaded = false`，使下次 `getActivePreset()` 重新加载。或者更好的方案：GUI 操作直接修改内存中的预设对象（当前已是如此，因为 Map 中的引用是共享的），只需确保 `savePresets()` 正确序列化即可。

### 4.2 修复方案

#### 4.2.1 `TaskPriorityManager` 修复

```java
// 新增 reset() 方法
public static void reset() {
    presets.clear();
    activePresetName = "";
    loaded = false;
}
```

在 `TaskAutoSwitchHandler.onServerStopped()` 中调用 `TaskPriorityManager.reset()`。

#### 4.2.2 预设名称冲突修复

```java
private void newPreset() {
    int num = TaskPriorityManager.getPresetNames().size() + 1;
    String name = "预设 " + num;
    while (TaskPriorityManager.getPresetNames().contains(name)) {
        num++;
        name = "预设 " + num;
    }
    // ... 创建预设 ...
}
```

#### 4.2.3 切换前提交编辑

```java
private void switchPreset(int direction) {
    commitPresetName(); // 先提交当前编辑框内容
    // ... 原有切换逻辑 ...
}

private void commitPresetName() {
    if (presetNameField == null) return;
    String newName = presetNameField.getValue().trim();
    if (!newName.isEmpty() && !newName.equals(editingPreset.getName())) {
        TaskPriorityManager.renamePreset(editingPreset.getName(), newName);
        activePresetName = newName;
    }
}
```

#### 4.2.4 多女仆兼容性确认

- **确认**：`TaskSwitchDecisionEngine.evaluateNormalSwitch()` 在服务端主线程中通过 `TaskPriorityManager.getActivePreset()` 获取预设。由于服务端主线程是单线程的，且预设存储在静态 Map 中，不存在并发问题。✓
- **确认**：GUI 操作在客户端线程修改预设对象 → 客户端/服务端线程隔离。但在单人模式（integrated server）中，客户端和服务端共享同一 JVM，对同一个 `presets` Map 的操作在不同线程中进行。需要审查是否存在竞态。
  - **风险评估**：`LinkedHashMap` 不是线程安全的。客户端 GUI 线程的 `buildWidgets()` / `savePresets()` 和服务端 tick 线程的 `getActivePreset()` 可能并发访问。
  - **缓解方案**：将 `presets` 替换为 `ConcurrentHashMap`，`activePresetName` 改为 `volatile`。或者在 GUI 操作时通过 `server.execute()` 将修改提交到服务端线程。
  - **推荐**：使用 `ConcurrentHashMap` + `volatile`，因为当前的读写模式是"GUI 偶尔写、服务端频繁读"，CAS 开销可接受。

## 5. 界面重构（G3 + G4 + G6）

### 5.1 工作模式选择栏新增"自动切换工作"（G3）

#### 5.1.1 实现方案

在主模组的左侧工作模式选择列表中注入"自动切换工作"条目。有两种实现路径：

**方案 A：注册自定义 IMaidTask（推荐）**

注册一个虚拟的 `IMaidTask` 实现——`AutoSwitchTask`——到 `TaskManager`，其 `getUid()` 返回自定义 ResourceLocation（如 `tlm_sincerely:auto_switch`）。当此任务被选中时，自动切换逻辑接管。

优点：
- 与主模组的任务系统完全兼容
- 无需 Mixin 注入任务列表
- 任务图标、名称、tooltip 由标准 API 提供

缺点：
- 需要实现 `IMaidTask` 接口的所有方法（大多数返回空/默认值）
- `setTask()` 设置此任务后，女仆实际执行的是自动切换逻辑，语义略有偏差

**方案 B：Mixin 注入任务列表**

通过 Mixin 在 `AbstractMaidContainerGui.addTaskListButton()` 中注入额外的按钮条目。

优点：纯 GUI 层面的修改，不影响任务系统

缺点：
- 需要 Mixin 主模组的 GUI 类（侵入性更高）
- 分页逻辑需要配合修改
- 任务列表中的条目与实际 `IMaidTask` 不对应，可能导致主模组其他逻辑困惑

**推荐方案 A**。具体设计见 5.1.2。

#### 5.1.2 `AutoSwitchTask` 设计

```java
public class AutoSwitchTask implements IMaidTask {
    public static final ResourceLocation UID = 
        new ResourceLocation("tlm_sincerely", "auto_switch");
    
    @Override
    public ResourceLocation getUid() { return UID; }
    
    @Override
    public ItemStack getIcon() { 
        // 使用时钟或自定义图标

    }

    @Override

        // 空闲行为——实际工作由 TaskAutoSwitchHandler 切换到具体任务
        return List.of();
    }
    
    @Override

        return PriorityConfig.ENABLED.get(); 
    }
    
    // getName() 由语言文件 gui.tlm_sincerely.task.auto_switch 提供
}
```

> **关键行为**：当女仆被设置为 `AutoSwitchTask` 时，`TaskAutoSwitchHandler` 检测到当前任务为 `auto_switch`，从预设的排序列表中选择第一个 AVAILABLE 的任务并通过 `maid.setTask()` 切换过去。切换后女仆的当前任务变为实际任务，但 `TaskAutoSwitchHandler` 继续监控并可能再次切换。
> 
> **注意**：这意味着需要修改 `TaskAutoSwitchHandler` 的入口逻辑。当前它检查 `maid.getScheduleDetail() == Activity.WORK` 后遍历所有工作中的女仆。v2 需要改为：**任何被设置为 `auto_switch` 任务的女仆，或正在被自动切换系统管理的女仆**，都参与检测循环。

### 6.1 移除数字优先级

#### 6.1.1 数据模型变更

**`TaskPriorityPreset`**：

- 移除 `Map<ResourceLocation, Integer> priorities` 字段
- 保留 `List<ResourceLocation> order` 字段作为唯一排序依据
- 列表中的位置即为优先级：索引 0 = 最高优先级

```java
public class TaskPriorityPreset {
    private String name;
    private final List<ResourceLocation> order;  // 位置即优先级

    public void addTask(ResourceLocation taskId) {
        if (!order.contains(taskId)) order.add(taskId);
    }
    
    public void removeTask(ResourceLocation taskId) { order.remove(taskId); }
    
    public void moveTaskUp(ResourceLocation taskId) { /* 索引 - 1 */ }
    public void moveTaskDown(ResourceLocation taskId) { /* 索引 + 1 */ }
    
    public List<ResourceLocation> getSortedTasks() { return Collections.unmodifiableList(order); }
    
    public int getTaskIndex(ResourceLocation taskId) { return order.indexOf(taskId); }
}
```

#### 6.1.2 JSON 格式变更

**旧格式**（向后兼容读取）：
```json
{
  "active": "默认预设",
  "presets": [{
    "name": "默认预设",
    "priorities": [{"task": "touhou_little_maid:attack", "priority": 1}],
    "order": ["touhou_little_maid:attack"]
  }]
}
```

**新格式**：
```json
{
  "version": 2,
  "active": "默认预设",
  "presets": [{
    "name": "默认预设",
    "order": ["touhou_little_maid:attack", "touhou_little_maid:farm"]
  }]
}
```

**迁移逻辑**（`TaskPriorityManager.loadPresets()`）：

1. 读取 JSON，检查 `version` 字段
2. 若无 `version` 或 `version == 1`：旧格式
   - 读取 `priorities` 数组提取 taskId 和 priority 数字
   - 按 priority 数字**升序**排序（数字小 = 优先级高）
   - 同 priority 的保持 `order` 列表中的相对顺序
   - 合并后写入 `order` 列表
   - 保存时写入新格式（`version: 2`，无 `priorities`）
3. 若 `version == 2`：新格式，直接读取 `order`

#### 6.1.3 决策引擎适配

`TaskSwitchDecisionEngine.evaluateNormalSwitch()` 中的排序逻辑：

- 旧：先按 priority 数字排序，同 priority 按 order 列表顺序
- 新：直接按 `order` 列表顺序（索引越小优先级越高）

#### 6.1.4 AI Tool 适配

`TaskPriorityTool` 的 `set` action：
- 旧：`set(taskId, priority)` 设置数字优先级
- 新：`set(taskId, position)` 将任务移动到指定位置（1 = 最高优先级）；或改为 `add(taskId)` + `move(taskId, position)`

### 6.2 滚轮改为滚动列表

#### 6.2.1 当前行为

`TaskPriorityScreen.mouseScrolled()` 在右栏区域滚轮时修改光标所在条目的数字优先级。

#### 6.2.2 新行为

- **左栏**：滚轮滚动"可选工作模式"列表（分页或虚拟滚动）
- **右栏**：滚轮滚动"已配置顺序"列表

```java
@Override
public boolean mouseScrolled(double mouseX, double mouseY, double scrollY) {
    if (isInLeftColumn(mouseX, mouseY)) {
        leftScrollOffset += (scrollY > 0) ? -1 : 1;
        leftScrollOffset = Mth.clamp(leftScrollOffset, 0, maxLeftScroll);
        buildWidgets();
        return true;
    }
    if (isInRightColumn(mouseX, mouseY)) {
        rightScrollOffset += (scrollY > 0) ? -1 : 1;
        rightScrollOffset = Mth.clamp(rightScrollOffset, 0, maxRightScroll);
        buildWidgets();
        return true;
    }
    return super.mouseScrolled(mouseX, mouseY, scrollY);
}
```

## 8. 风险与缓解

| # | 风险 | 影响 | 缓解 |
|---|------|------|------|
| R1 | 主模组无公开的 `IMaidTask` 注册 API | 阶段 5 受阻 | 退回方案 B（Mixin 注入任务列表），或通过反射/AT 访问 `TaskManager` 的注册方法 |
| R2 | `TaskButton` 无法被 Mixin（remap 或 classloader 问题） | 红色渲染提醒无法实现 | 退回方案 c（`AutoSwitchTask.getName()` 返回带颜色的 `Component`） |
| R3 | 任务模式 Tab 页的 GUI 工厂不可扩展 | 阶段 6 受阻 | 保留独立 `TaskPriorityScreen`，SideTab 按钮打开独立界面（回退到当前方案但 UI 改进） |
| R4 | 旧配置文件迁移失败 | 用户丢失已配置的预设 | 迁移逻辑加 try-catch，失败时保留旧文件并创建新默认预设；在日志中输出详细迁移信息 |
| R5 | `ConcurrentHashMap` 替换后的性能影响 | 可忽略 | 当前读写频率极低（GUI 偶尔写、服务端每 100 tick 读一次） |
| R6 | 默认值从 `false` 改为 `true` 导致老用户困惑 | 已有 `Enabled=false` 配置的用户不受影响 | 在 changelog 中说明；新用户开箱即用 |
