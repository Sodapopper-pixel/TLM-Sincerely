## 1. 背景与问题

M-1 之后记忆系统仍有一组结构性缺陷，两轮独立评审结论收敛一致：

| # | 问题 | 现状 |
|---|------|------|
| P1 | 引导走 Skill 层存在**触发悖论** | `memory-guidance` 是惰性 skill，模型须自行决定调 `use_skill` 才能拿到引导；而"何时该记"恰是引导要教的内容。意识不到要记 → 不加载引导 → 静默不写入，且不可复现 |
| P2 | 无检索机制 | 只有全量索引预览 + 精确 key recall。F3 移除 key enum 后，索引预览成为模型发现已有 key 的唯一途径，记忆一多即"存得进、找不到" |
| P3 | 无容量策略 | 满容时 Tool 拒绝写入并提示模型自行 `forget`：多烧 ≥2 个 tool 轮次、决策推给对话中的模型、该淘汰的长期不淘汰 |
| P4 | 无整理与遗忘机制 | 相似/重复记忆永不合并，容量被低价值条目蚕食；手动命令整理破坏沉浸感，玩家期望后台静默处理 |
| P5 | 多人归属缺失 | 多玩家共享女仆记忆，无来源标注（远期待办） |

另有成本事实（影响注入位置决策）：TLM 协议无状态，每次请求重发 `[system(+guidance)(+summary) + 全量 history + 当前 user(含 context)]`；已核实 **history 存的是不含 `<context>` 的原文**（CONTRACT §2.1 步骤 7）。因此引导文案放 system 与放 context **同为每请求 O(1)**，位置不是成本变量，文案长度才是；反而 `use_skill` 的正文作为 tool result 进 history，会在 history 中持续计费，直到被摘要压缩或队列驱逐。

### 1.1 主模组 history / 压缩事实（1.5.3 源码，替代旧「24 条窗口」说法）

| 项 | 1.5.3 实际 | 来源 |
|----|------------|------|
| History 硬上限 | `CappedQueue<>(512)`，超出后从最旧端 `pollLast` | `MaidAIChatData` 构造 |
| 压缩触发 | **上一轮**普通聊天返回的 token 用量 ≥ `MaidHistoryCompressTokenLimit`（默认 **48K** token，配置单位 K，范围 8–1024） | `AIConfig` + `tryCompressBeforeChat` |
| 触发时机 | 玩家新开 `chat()` **之前**；命中则先异步摘要，完成后再跑本次 `tryToChat`（玩家消息被推迟，不丢失） | `MaidAIChatManager.chat` |
| 保留最近 | 最近 **32** 条不压缩；可压缩数 = `size - 32`；可压缩数 &lt; **4** 则跳过 | `HistorySummaryManager` / `MIN_MESSAGES_TO_COMPRESS` |
| 摘要落盘 | `compressedSummary` 字符串，截断至 **1600** 字符；作为 **第二条 system** 注入（`## Compressed Conversation Summary`） | `appendSummaryMessage` / `MAX_SUMMARY_LENGTH` |
| 并发 | `historySummaryRunning` 为 true 时**不**再开压缩，本次聊天直接用未压缩上下文 | `tryScheduleHistorySummary` |
| 失败 | 空白摘要 / 快照尾部不匹配 / 请求失败 → 放弃本轮压缩，仍继续玩家聊天 | `completeHistorySummary` / `HistorySummaryCallback` |
| 发请求前清理 | `HistoryMessagesCheck` 去掉孤儿 TOOL、不完整 tool_call 配对 | `HistoryMessagesCheck.checkMessages` |

> **对 M-2 的含义**：维护轮不能再指望「24 条自然老化」；history 最长可驻留数百条，**必须**在维护结束后主动清理本轮消息（V2 已核实可行：`getHistory().getDeque()` 可增删）。维护轮自身也会贡献 token，可能间接触发主模组摘要压缩——静默与 history 清理因此更关键。

## 2. 设计决策（已确认）

| # | 决策 | 要点与理由 |
|---|------|-----------|
| D1 | 移除 `memory-guidance` skill，引导压缩后经 **mixin 注入第二条 system 消息** | 消除触发悖论；system 角色对行为指令遵从度高于 user 消息内的 `<context>`；行为准则（静态）与记忆索引（动态）分离。mixin 基建：`tlm_sincerely.mixins.json` 为 `required:true`/`defaultRequire:1`；**注意：当前 `mixins` 服务端数组为空**，`MaidChatBroadcastMixin` 源码存在但未登记——M-2.4 须同时登记服务端 mixin |
| D2 | `tlm_memory` 新增 `search` action（key+value 子串匹配） | F3 之后模型唯一的存量发现手段；解锁后续预览瘦身（keys-only）这一真正的 token 大头节省；纯 Java 确定性逻辑，golden 可测 |
| D3 | 满容**自动淘汰**最旧 archive，core 永不自动淘汰 | 单轮完成、无模型自由裁量；tool result 明确告知淘汰了谁；配置可回退旧拒绝行为 |
| D4 | MemoryEntry 增加访问统计（`lastAccessedAt`/`accessCount`） | 仅 `recall`（全文读取=真实使用）计数，`search` 命中不计数以防膨胀；为将来 LFU 淘汰序与重要性晋升打底；v1 淘汰仍按最旧 |
| D5 | **后台自动整理**：阈值触发维护对话轮，新增 `merge` action，**工具层硬约束只允许触碰 archive**；提示词约束负责合并质量 | 玩家不应为记忆维护手动跑命令（沉浸感）。安全原则：**提示词让模型做得对，工具层让模型错不出界**——即使模型违规调用也碰不到 core；维护轮额外限制可用 action 集；全程静默（不广播、不冒泡、不 TTS、不 thinking 副文，仅服务端日志审计） |
| D6 | `summarize` 提示词自包含 | 现文案引用 "Use the memory-guidance skill"，skill 移除后必须内联"什么值得记"标准 |
| D7 | 多人归属用 MemoryEntry `source` 字段，**不做**按玩家 key 命名空间 | 记忆是女仆视角的，按玩家拆 key 会破坏女仆对"玩家"的整体认知；来源只在 recall/预览中呈现（P2） |

## 5. 详细设计

### 5.1 search（M-2.1）

- 参数：`query`（必填，trim 后判空）、无其它参数；返回上限固定 10 条。
- 匹配：`lower(query)` 是 `lower(key)` 或 `lower(value)` 的子串即命中；按插入序返回。
- 返回格式：每行 `  <key>: "<preview>"`（preview 复用 `PreviewLength` 截断），footer `N matches`；无命中返回 `No memories match '<q>'.`。
- 不更新访问统计（D4）；不改动 schema 其它部分。

### 5.2 满容自动淘汰（M-2.2）

`MaidMemoryTool.remember` 在 F2（trim 判重）之后、`set` 之前：

```
若 size() >= MAX_MEMORIES 且 key 不存在:
    若 AutoEvict 关 → 维持现文案拒绝
    否则 取插入序首个 archive 条目:
        有 → forget(evictKey) → set(new) → save
             返回 "Remembered 'k' = "v" (<imp>). Evicted oldest archive '<old>' to make room."
        无（全 core）→ "Memory limit reached (N max) and all entries are core.
                        Ask the player which memory to forget."
```

- `MaidMemory.set` 本身不改（保持纯语义）；淘汰只发生在 Tool 层。
- 新增配置 `AutoEvict`（bool，默认 `true`）。

### 5.3 访问统计（M-2.3）

- `MemoryEntry` 扩展为 `(value, importance, createdAt, updatedAt, lastAccessedAt, accessCount)`。
- JSON：写出恒带两字段；加载缺省 `0`（向后兼容旧存档）。
- 更新点仅 `recall` 成功路径：`accessCount++`、`lastAccessedAt=now` 后保存。频率低，沿用即时写盘；若后续 IO 毛刺明显再引入延迟写（留扩展点，不在本期）。
- v1 不改变淘汰/注入行为，纯打底 + 可观测（`/tlmmemory get` 展示统计）。

### 5.4 system 注入引导（M-2.4）

**注入机制**：新增服务端 mixin（登记进 `tlm_sincerely.mixins.json` 的 `mixins` 数组），目标 `MaidAIChatManager.buildMessage`（private，可用 name/desc 注入）。在 `LLMMessage.systemChat(maid, setting)` 入 list **之后**、`appendSummaryMessage` **之前**插入引导 system 消息。

消息次序：

```
[setting][memory-guidance][summary?][history][user+context]
```

与主模组 `HistoryMessagesCheck` 兼容：开头连续 SYSTEM 均保留。

**配置**：`MemoryGuidance`（bool，默认 `true`）；关闭时不注入。

**同里程碑基建**：将已有 `MaidChatBroadcastMixin` 登记进服务端 `mixins`（当前未生效），为 M-2.6 静默打底。

**引导文案（草案，约 150 token，实施时冻结为常量并纳入 golden）**：

```text
## Memory Guidelines
You have persistent memory, listed under "Maid persistent memories" in context. Manage it with the tlm_memory tool.
Call remember when: the player explicitly asks you to remember; the player states a lasting preference, personal fact, or preferred form of address; a significant event occurs (gift, promise, milestone).
Do NOT remember: small talk, weather, transient game state, anything not said to you directly, anything already available via query_game_context.
Key: short semantic English snake_case (e.g. player_hobby). Value: one concise sentence with context (who/what/when). Importance: core = explicitly requested or relationship-defining; archive = contextual details.
Forget only when the player explicitly asks. Capacity is limited; when full, the oldest archive entry is evicted automatically.
Use search to find old memories, recall to read full detail.
```

**同步删除/改写**：

- 删除 `src/main/resources/data/touhou_little_maid/skills/memory-guidance/skill.md` 及 harness fixtures 副本；
- `summarize` 提示词改为自包含（D6），草案：

```text
Please review our conversation so far and use tlm_memory remember to record anything you missed: things the player asked you to remember, lasting preferences, personal facts, significant events. Use short semantic English keys and one concise sentence with context. Do not record small talk or transient game state.
```

### 5.5 merge action（M-2.5）

| 项 | 契约 |
|----|------|
| 参数 | `keys`：2–5 个源 key（数组或逗号分隔，以 V3 为准）；`key`：目标 key；`value`：合并后的值 |
| 硬校验（Tool 层，任一失败即整体拒绝、不改状态） | 每个源 key trim 后存在；每个源条目 `importance == archive`；源互不相同；数量 2–5；目标 key 不得与现有 core 冲突；key/value 走 `MaidMemory.set` 既有校验 |
| 成功语义 | 原子：逐个 forget 源 → set 目标（archive）→ save；返回 `Merged <n> entries into '<key>'` |
| 失败文案 | `merge can only combine existing archive memories; core entries are protected.`（风格对齐 invalidParam） |

**设计原则**：archive-only 是工具层不变量，不是提示词愿望。整理提示词可以失效，core 不会因此被合并或删除。

### 5.6 后台自动整理（M-2.6）

**触发**（在 `remember` 成功写盘后判断，命中则登记待办，**下一服务端 tick** 调度执行，避免在 tool 回调内重入 `chat()`）：

```
TidyEnabled 开
且 size() >= ceil(MaxMemories * TidyThreshold)
且 now - lastTidyAt >= TidyCooldownMinutes
且 主人在线且为 ServerPlayer（chat 需要 sender）
且 LLM site 可用
```

**状态持久化**：`lastTidyAt` 存入女仆记忆 JSON 根级 `meta` 对象（`{"memories": {...}, "meta": {"lastTidyAt": ...}}`），加载缺省 0；旧存档兼容。

**维护轮执行**：复用 summarize 同款机制 `chatManager.chat(tidyPrompt, ...)`，但进入前置位**维护模式**标记（每女仆）：

1. **action 收窄**：维护模式期间 `tlm_memory` 仅接受 `search` / `recall` / `merge`，其余 action 返回 `Only search/recall/merge are allowed during memory maintenance.`——模型即使想"顺手"remember/forget 也做不到；
2. **静默（全出口）**：
   - 聊天栏：`MaidChatBroadcastMixin`（或等价注入）检查维护标记，跳过 `sendSystemMessage` / 广播；
   - 气泡：拦截/跳过 `addLLMChatText` 与 thinking/waiting 气泡更新；
   - TTS：维护模式跳过 `tts()` 播放路径；
   - 玩家不可见，仅服务端日志；
3. **审计**：服务端日志输出 `Maid <uuid> consolidated [a, b] -> <key>`；
4. **history 收尾（优先，非可选）**：维护结束（成功/空转/失败）后，从 history 新端移除本轮产生的 user/assistant/tool 消息（按维护开始前的 `history.size()` 快照 diff，或消息内容指纹）。**不得**依赖 512 上限或主模组摘要压缩来「冲掉」维护污染；
5. **冷却**：无论成败均刷新 `lastTidyAt` 并清除维护标记；失败按冷却自然退避，不做重试循环。

**维护提示词（草案，自包含，user 消息附带 archive 全量列表——merge 硬约束已保证安全，只注 archive 兼顾省 token 与降低诱导）**：

```text
You are performing memory maintenance. Below is the full list of archived memories.
Identify groups of entries that describe the SAME fact or event, not merely related topics.
For each group, call tlm_memory action=merge with the source keys and one merged value that preserves every concrete detail (who/what/when/where).
Do not merge entries that are only topically related. Prefer fewer, well-merged entries.
If nothing needs merging, reply exactly "No maintenance needed." and make no tool calls.
```

**与主模组压缩的交互**：维护轮若推高 `lastChatTokenUsage`，可能使**下一次玩家聊天前**触发 `tryCompressBeforeChat`。因维护消息应已从 history 删除，摘要输入中不应再含维护正文；若清理失败，摘要可能吞进维护噪声——验收须覆盖「维护后 history 无维护痕迹」。

### 5.7 source 多人归属（M-2.7，可选）

- `MemoryEntry` 增加 `source`（写入玩家名/UUID，服务端在对话入口已知）；JSON 缺省空。
- `recall` 返回与预览可选呈现来源（新增配置 `ShowSource`，默认关）；命令侧 `set/set-core` 记录执行玩家。
- 明确不做按玩家 key 命名空间（D7）。

### 5.8 预览瘦身（M-2.8，可选）

search 上线后，archive 预览可从「key+截断值」降级为纯 key 列表（新增配置 `PreviewMode = full | keys_only`），50 条记忆的每请求开销从 ~300-500 token 降至 ~100。默认维持 `full`，待 search 行为验证后再评估切换。

## 7. 风险与对策

| 风险 | 对策 |
|------|------|
| TLM 升级致 mixin 目标变动 | `required:true` + `defaultRequire:1` 使构建/加载直接失败；V1 结论记入 CONTRACT，升级 TLM 时按清单复核 |

## 附录 A · 主模组 history 压缩流程（实施参考）

```
玩家 chat(message)
  │
  ├─ lastChatTokenUsage >= 48K token ?
  │     否 → 直接 tryToChat
  │     是 → tryScheduleHistorySummary
  │            ├─ 已有 summary 在跑 / 可压缩 < 4 / site 无效 → 直接 tryToChat（不吞消息）
  │            └─ 快照最旧 (size-32) 条 → 异步 LLM 摘要（无 tools）
  │                   ├─ 成功：写 compressedSummary(≤1600) → pollLast 删除快照条数
  │                   │        → lastChatTokenUsage=0 → 再执行本次 tryToChat
  │                   └─ 失败/空白/快照不匹配：stop flag → 仍执行本次 tryToChat
  │
  tryToChat:
    buildMessage = [SYSTEM setting][+ SYSTEM guidance←本附属][+ SYSTEM summary?][+ history]
    HistoryMessagesCheck（清孤儿 tool）
    normalChat: user = <context>…</context>\n原文
                history 只存原文
```

摘要请求本身**不**走普通对话 history，是独立两消息请求（system 压缩指令 + user 含 Existing summary / Older messages）。单条 tool/system 在摘要输入中截断至 300 字符；assistant 只保留 chat text 或 tool 名列表。
