## 1. 背景与目标

### 1.1 问题

简易记忆系统已落地（Context 注入、`tlm_memory` Tool、`memory-guidance` Skill、命令与 JSON 持久化），但迭代与排错仍高度依赖 `runClient` 进档对话：

- 改 skill / tool description / preview 算法后反馈慢；
- 难以稳定复现「该记不记 / 不该记却记 / 预览看得到但 recall 不对」；
- 无法系统对照主模组完整 prompt（system + context + history + tools）；
- 配置旋钮（`CoreLimit`、`PreviewLength`、`MaxMemories`）对模型行为的影响缺乏可观测手段。

### 1.2 目标

在不启动 Minecraft 的前提下，构建独立测试环境，使下列能力可复现、可观测、可回归：

1. **记忆域逻辑**：`MaidMemory` 读写、容量、core/archive、`generateContextPreview`、JSON 格式与游戏内一致；
2. **主模组 AI 协议**：用户消息 `<context>` 注入、OpenAI 兼容 LLM 接入、Tool 多轮循环、Skill 加载与 `use_skill`；
3. **记忆相关 AI 功能**：`tlm_memory`、`query_game_context`（按需分类）、`memory-guidance`、summarize 补记；
4. **Web 前端**：对话、虚拟游戏环境参数、记忆 Inspector、本轮 prompt/tool trace、配置旋钮、场景预设；
5. **场景断言**：用结构级检查快速验证 skill/tool/config 改动是否破坏预期行为。

### 1.3 非目标（首期明确不做）

- 完整模拟 Minecraft 世界 tick、路径、背包物理、实体 AI；
- TTS / STT / 聊天气泡 / Brigadier 命令树；
- 将 Node 依赖并入 Forge 构建或发布 jar；
- knowledge 类型 Skill 的 RAG 子对话（可预留扩展点）；
- 多女仆并发完整模拟（可后期加 multi-session）。

## 3. 主模组协议契约（必须对齐）

实施前以本仓库依赖的 Touhou Little Maid 源码/文档为准，对照路径：

- `UserPromptContexts`：用户消息 context 注入
- `MaidAIChatManager.buildMessage`：system + 可选摘要 + history
- `LLMCallback`：tool 循环、上限与去重
- `wiki-reference/docs/wiki/dev/ai/{overview,context,tool,skill}.md`

### 3.1 消息结构

```
messages =
  [ SYSTEM: 女仆设定 ]
  + [ SYSTEM: 历史摘要? ]   // 首期默认关闭
  + [ ...history 从旧到新 ]
  + [ USER: <context>\n...\n</context>\n玩家原文 ]
```

Context 块：

- 起止标签：`<context>` / `</context>`
- 行格式：`- <label>: <value>`（与 `AbstractMaidContext` 展示一致）
- 自动注入分类（`promptContext=true`）每轮写入用户消息；不出现在 `query_game_context` 可选列表
- 按需分类（`promptContext=false`）仅在 tool 查询时返回

记忆 Context：

- 分类：`tlm_sincerely_memory_list`（`MaidMemoryContext` 构造第一参数；契约值一律以源码为准并标注来源类，勿凭记忆摘录）
- label：`Maid persistent memories`（`MaidMemoryContext`）
- value：`generateContextPreview(coreLimit, previewLength)`；关闭时 `Memory system disabled`；空时 `None`

### 3.2 Tool 循环护栏（对齐 LLMCallback）

| 规则 | 值 |
|------|-----|
| 最大 tool 轮次 | 16 |
| 同批签名连续重复上限 | 2 |
| 同批完全相同 tool_call | 去重后执行 |
| tool 结果 | 以 tool role + 对应 `tool_call_id` 写回 messages 再请求 LLM |
| 未知 tool / 参数解析失败 | 将错误文案写入 tool result，让模型自纠，不整批中断 |

### 3.3 记忆 Tool 语义（对齐 MaidMemoryTool）

| action | 必填 | 行为要点 |
|--------|------|----------|
| `remember` | key, value；importance 默认 archive | 满容量且 key（trim 后）不存在 → 返回 limit 文案；成功则 save |
| `recall` | key | 返回 `[importance] key: value`；不存在则列出 available keys |
| `forget` | key | 删除并 save |
| 任意 | — | `Enabled=false` → `Memory system is currently disabled.` |

参数 schema 构建时：已有 key 作为 `key` 字段 enum 动态填入（每轮按当前记忆刷新）。

> ⚠️ 已知怪癖（M-1 F3 决策）：`key` 的 enum 只含现有 key，但 `remember` 恰恰要写**不在** enum 中的新 key——strict 模式 provider 会拒绝，宽容 provider 仅作提示。
>
> **定案（2026-08-06）**：**去掉 `key` 字段的 enum**，不再在 `parameters()` 中枚举现有 key。理由：(1) 单一 tool schema 无法按 action 分支给 key 不同 schema，故「enum 仅挂 recall/forget」不可行；(2) recall/forget 在 key 缺失/不存在时已通过错误文案返回 `Available keys: [...]`，preview 也已展示全部 key，enum 属冗余且主动伤害 `remember`；(3) 去掉 enum 后空记忆天然不生成 `enum: []`。`key` 字段 description 改为提示「remember 可用新 key；recall/forget 用现有 key（见 preview 或 Available keys）」。

校验与截断（对齐 `MaidMemory.set`）：

- key trim 后非空，最长 64；
- value trim 后非空，最长 500；
- importance 仅 `core` / `archive`，非法则归为 archive；
- 新建受 `MaxMemories` 限制，更新已有 key 不受「条数已满」拦截（与 Tool 层「满且非覆盖」逻辑一致）；
- Tool 层满容判断与 `set` 内部一律按 trim 后的 key 判重（M-1 F2 修复后的一致性要求）。

### 3.4 JSON 持久化格式（与游戏内 1:1）

路径约定（harness 使用独立数据目录，可导入游戏文件）：

```
<harness-data>/maid_memories/<uuid>.json
```

格式：

```json
{
  "memories": {
    "<key>": {
      "value": "...",
      "importance": "core" | "archive",
      "createdAt": 0,
      "updatedAt": 0
    }
  }
}
```

必须能与 `config/tlm_sincerely/maid_memories/<uuid>.json` 互导且语义一致。

实现注意：

- Java 侧 Gson `setPrettyPrinting`（2-space 缩进）；golden 做字节级比对须对齐格式，否则用语义级比对
- 加载后键序须与文件内顺序一致（Java 为 `LinkedHashMap`；TS 侧同样按插入序维护，preview 输出依赖此顺序）
- 游戏内 `load` 失败静默返回空记忆、`save` 失败静默忽略；TS 镜像保持同等语义，但 harness UI/CLI 应显式报错便于排错

### 3.5 Skill

- 加载 `memory-guidance/skill.md`（YAML front matter + body）
- 通过 `use_skill` 注入 body 到对话（普通 skill，非 knowledge RAG）
- name / description 规则对齐主模组 Skill 文档

### 3.6 Summarize

对齐 `/tlmmemory summarize` 注入的固定用户意图（可做成 API/按钮，不经 Brigadier）：

```
Please review our conversation so far and use tlm_memory remember
to record any important information you may have missed.
Use the memory-guidance skill to decide what is worth remembering.
```

## 4. 系统架构

```
┌─────────────────────────────────────────────────────────────┐
│ Web (packages/web)                                          │
│  对话 │ 虚拟环境 │ 记忆 Inspector │ Config │ Debug Trace      │
└───────────────────────────┬─────────────────────────────────┘
                            │ HTTP / SSE
┌───────────────────────────▼─────────────────────────────────┐
│ Server (packages/server)                                    │
│  Session 管理 │ 鉴权无（本机）│ 静态前端托管（可选）              │
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│ Agent (packages/agent)                                      │
│  VirtualMaid 快照 │ Context Builder │ Tool Registry          │
│  Skill Loader │ Agent Loop │ OpenAI-compatible Client        │
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│ Core (packages/core)                                        │
│  MaidMemory 等价实现 │ JSON Store │ Preview │ 契约类型/序列化   │
└─────────────────────────────────────────────────────────────┘
```

### 4.1 VirtualMaid（替代 EntityMaid）

纯数据快照，前端可编辑，每轮 chat 前由 Context Builder 读取：

| 分组 | 字段（最低集） |
|------|----------------|
| 身份 | `uuid`, `name`, `language`, `systemPrompt` |
| status（自动注入） | `health`, `maxHealth`, `isSleeping`, `isFollowing`, `sitting`, `riding?`, `schedule`, `activity`, `task` |
| world（自动注入） | `timeOfDay`, `weather`, `dimension`, `biome` |
| 按需 user | `userName`, `userHealth`, `userMainHand?` |
| 按需 equipment / effects / position / nearby | 可选结构，供 `query_game_context` |

`systemPrompt` 首期用可编辑模板，不实现主模组 PAPI 全量展开。

### 4.2 Context Builder

- 注册分类表：内置 `status` / `world`（自动）+ 按需分类 + `tlm_sincerely_memory_list`（自动，接记忆 store）
- 输出与游戏内相同的 `<context>` 文本块
- 配置变更（Enabled / CoreLimit / PreviewLength）立即影响下一轮注入

### 4.3 Tool Registry

| Tool ID | 实现深度 | 说明 |
|---------|----------|------|
| `tlm_memory` | **完整** | 测试主体 |
| `use_skill` | **完整**（普通 skill） | 加载并注入 skill body |
| `query_game_context` | **完整** | 按 VirtualMaid + 分类表返回 |
| `switch_follow_state` 等 | **stub** | 固定成功文案；可配置全局禁用以免干扰 |
| `query_minecraft_wiki` | **stub 或禁用** | 默认禁用，避免外网与噪声 |

### 4.4 Agent Loop

1. 读取 session：VirtualMaid、memory、config、history  
2. `userMessage = <context> + 原文`  
3. `messages = [system, ...history, user]`  
4. 请求 LLM（tools schema 按当前 maid/memory 动态生成）  
5. 若有 `tool_calls`：执行 → 追加消息 → 受护栏约束循环  
6. 最终 assistant 文本写入 history；推送 SSE 事件  
7. 每次记忆变更推送 `memory_diff`

History 首期：固定上限条数的滑动窗口；**不实现**主模组 HistorySummary 压缩（接口预留，默认关）。

### 4.5 数据与安全

- 会话与记忆默认落在 `tools/memory-harness/data/`（gitignore）
- API Key：`tools/memory-harness/.env`（gitignore）；提供 `.env.example`
- 服务默认仅监听 `127.0.0.1`
- 导入游戏记忆：用户显式选择文件/目录，不默认扫描 `run/`

### 4.6 LLM Transport（live / record / replay）

LLM 客户端抽象为 `LLMTransport` 接口，三种可切换模式：

| 模式 | 行为 | 用途 |
|------|------|------|
| `live` | 真实调用 provider | 手聊调参 |
| `record` | 真实调用，并按轮落盘请求/响应 | 把「表现良好」的模型行为留成快照 |
| `replay` | 不出网，按会话内轮序回放录制响应 | 场景回归 CI、改 skill/description 后同轮重放 diff |

录制文件落在 `data/recordings/<场景或会话名>/`（gitignore）。replay 按轮序匹配即可，不依赖 provider 返回的确定性。该机制是「改文案反馈慢」痛点的直接解法：同一份录制在旧/新 skill 文本下各重放一次，对比 tool 轨迹。

### 5.1 SSE 事件类型（建议）

| event | 载荷要点 |
|-------|----------|
| `context` | 本轮注入的 context 原文 |
| `assistant_delta` | 流式文本（若提供商支持；否则可只发 final） |

| `tool_result` | id, content, summary |
| `memory_diff` | added / updated / removed |
| `final` | 完整 assistant 文本 |
| `error` | 可展示错误 |
| `trace_ready` | 可拉取完整 trace |

## 6. 前端（packages/web）

### 6.1 布局

三栏单页：

| 区域 | 内容 |
|------|------|
| 左 | 会话列表、场景预设、虚拟环境表单（天气/任务/血量/昵称等）、记忆配置旋钮 |
| 中 | 对话气泡、tool 调用折叠条、输入框、Summarize 按钮 |
| 右 | 记忆 Inspector（★core / ·archive）、增删改、导入导出 |
| 底/抽屉 | Debug：本轮 raw messages、tools schema、本轮 prompt/completion token 统计（必备——调 CoreLimit/PreviewLength 的核心观测量） |

原则：**可观测性优先于游戏感 UI**。

### 6.2 关键交互

1. 发送消息后实时展示 tool 调用摘要（如 `tlm_memory { remember player_hobby }`）  
2. tool 成功后右侧记忆列表 diff 高亮  
3. 修改环境/配置不自动发聊天，但明确提示「将影响下一轮 context」  
4. 一键复制完整 messages JSON  
5. 导入 `maid_memories/*.json` 后 Inspector 与 export context 立即可用  
6. 加载场景预设重置 env + memory +（可选）历史

## 7. 契约与回归

### 7.1 Golden（确定性，无 LLM）

| 套件 | 内容 |
|------|------|
| `preview` | 给定 memories + coreLimit + previewLength → 期望 preview 字符串 |
| `json-roundtrip` | load/save 与样例文件字节级或语义级一致 |
| `context-build` | VirtualMaid 快照 + 记忆 → 完整 `<context>` 块 |
| `tool-local` | 不调用 LLM，直接调 `tlm_memory` 实现，断言返回文案与 store 状态 |

Java 侧（必做）：`src/test/java` 使用**同一批** `fixtures/golden` JSON——期望值由 Java 权威实现的一键生成工具产出（禁止手抄），Java 单测与 TS 测试双向读取，任一侧改动权威算法都会立即暴露失步。

### 7.2 场景包（需 LLM，结构断言为主）

| ID | 意图 | 结构期望（示例） |
|----|------|------------------|
| `pref-remember` | 玩家要求记住偏好 | 出现 `tlm_memory.remember`；store 新增合理条目 |
| `no-remember-weather` | 仅评论天气 | **不**新增临时天气类记忆（或 key 黑名单断言） |
| `recall-from-preview` | archive 仅预览，问细节 | 出现 `recall`；最终回复依赖全文信息 |
| `forget-on-request` | 要求忘记 | 出现 `forget`；对应 key 删除 |
| `capacity-full` | 已满再记 | tool 返回 limit，或按 skill 先 forget archive 再 remember |
| `core-vs-archive` | 明确核心约定 | `importance=core` |
| `summarize-missed` | 多轮后补记 | summarize 后 store 出现遗漏偏好 |
| `query-not-memory` | 问血量/坐标 | `query_game_context`，不写 memory |
| `skill-trigger` | 含「记住」类指令 | 调用 `use_skill(memory-guidance)` 或行为遵守指引（至少 store 合规） |
| `recall-wrong-key` | 模型用错 key 召回 | tool 返回 available keys；模型自纠后 recall 成功（精确 key 设计的最弱链路，重点验证） |
| `oversized-value` | 写入超 500 字符 value | 静默截断不报错；模型后续行为正常、不循环重试 |
| `core-limit-exceeded` | core 条目多于 CoreLimit | 超限 core 以降级预览可见（对应 M-1 F1 修复后行为） |

断言对象除最终 store 与 tool 调用外，允许断「本轮注入的 context 文本」（如 `recall-from-preview` 应断 preview 字符串确实出现在 user 消息中）。

评判优先级：

1. **结构断言**（tool 名、参数字段、最终 store、本轮 context）— CI 主路径  
2. 人工回放 trace — 改文案时对照  
3. LLM-as-judge — 可选，不作为首期门禁  

模型非确定性处理：对 key 名称允许「候选集合 / 正则」而非绝对字符串相等；关键路径可固定 temperature=0。

## 8. 里程碑

里程碑只描述交付物与验收条件，不绑定日历工期。后一里程碑默认依赖前一里程碑完成。

### M-1 — 模组侧前置修复（先行）

harness 的意义是锁死「当前行为」，因此已知缺陷必须先在游戏内修复，再进入 golden 冻结，否则镜像会把 bug 永久固化。

**交付物**

- **F1 preview 可见性修复**：`MaidMemory.generateContextPreview` 中超过 `coreLimit` 的 core 条目当前被完全跳过（`coreLimit=0` 时所有 core 记忆从 context 消失，footer 却仍计数 "X core"）。修复为：超限 core 条目降级为 archive 式预览（截断 + 引号格式），使 `CoreMemoryLimit=0` 与配置注释「0 = 全部仅预览」语义一致
- **F2 trim 一致性修复**：`MaidMemoryTool.remember` 的满容判断改用 trim 后的 key（与 `MaidMemory.set` 内部一致），消除 `" foo "` 与 `"foo"` 在满容时被误判为新 key 的边界
- **F3 key enum 决策（书面结论写入 §3.3 警告框）**：见 §3.3；确定 enum 去留方案并同步更新 tool description
- 修复后 `runClient` 冒烟验证一轮记忆对话

**验收**

- [ ] F1：coreLimit=0 与 core 超限场景下，全部记忆条目在 preview 中可见（core 全文或降级预览）
- [ ] F2：满容时 remember 已存在 key（含首尾空格变体）按更新处理而非拒绝
- [ ] F3 决策已写入 §3.3
- [ ] 修复未破坏现有游戏内行为（旧 JSON 正常加载）

### M0 — 契约与 Golden 基线

**交付物**

- 本文档确认的协议摘录落地为 `tools/memory-harness/fixtures/golden/` 与简短 `CONTRACT.md`（可与本文 §3 互链，避免双份漂移）；CONTRACT 中每个契约值标注来源类名（教训：category id 曾误摘为 `tlm_sincerely_memory`，实际为 `tlm_sincerely_memory_list`）

## 9. 实施顺序与依赖

```
M-1 模组侧前置修复（游戏内）
 └─► M0 契约/Golden
      └─► M1 Core（无 LLM）
           └─► M2 Agent + Server + 真 LLM（含 record/replay）
                ├─► M3 Web UI
                └─► M4 场景回归（可与 M3 并行启动，但 required 场景门禁建议在 M3 可手跑之后固化）
                     └─► M5 模组衔接（可选）
```

约束：

- M-1 未完成不得冻结 golden：golden 会把缺陷行为永久固化；
- **harness 是镜像不是实验场**：行为改进一律先落 Java → 重新生成 golden → 同步 TS；禁止在 TS 侧单方面「改进」行为，否则克隆与游戏分叉，比没有 harness 更危险；
- 未完成 M0/M1 不得宣称「与游戏 preview 一致」；
- 未完成 M2 不得开始堆砌复杂 UI 动效；
- stub tool 默认减少噪声；需要测「模型误调 switch」时可再开启；
- 不擅自 `runClient`、不擅自 git commit（遵循 `AGENTS.md`）。

## 10. 配置默认值（与 MemoryConfig 对齐）

| 项 | 默认 | 范围（UI/校验） |
|----|------|----------------|
| Enabled | true | bool |
| MaxMemories | 50 | 1–200 |
| CoreMemoryLimit | 10 | 0–50（0 = 全部仅预览） |
| ContextPreviewLength | 30 | 10–200 |

| 项 | 默认 | 说明 |
|----|------|------|

| enableHistorySummary | false | 预留 |
| enableStubSwitchTools | false | 是否注册 switch_* stub |
| temperature | 0（场景）/ 用户偏好（手聊） | |
| maxToolTurns | 16 | 与主模组一致，一般不改 |
| llmMode | live | live / record / replay（见 §4.6） |

## 11. 风险与缓解

| 风险 | 缓解 |
|------|------|
| 已知实现缺陷被 golden 固化 | M-1 前置修复先于 M0；golden 只冻结修复后行为 |
| 契约摘录漂移（如 category id 凭记忆写错） | CONTRACT 标注来源类名；golden 期望值由 Java 工具生成，禁止手抄 |
| 场景回归依赖密钥与调用成本 | record/replay 模式离线跑回归（§4.6） |
| TS 与 Java preview/tool 文案漂移 | 同源 golden；改 Java 必跑 M0/M1；M5 双边测试 |
| 主模组小版本改 prompt 格式 | CONTRACT 标注 TLM 版本；升级依赖时 diff `UserPromptContexts` / `LLMCallback` |
| LLM 非确定性导致场景 flaky | 结构断言 + temperature=0 + key 候选集；required 集控制规模 |
| 范围膨胀成完整 TLM 模拟器 | 非目标清单约束；仅保证记忆决策链 |
| 密钥与玩家档误提交 | `.gitignore` data/ 与 `.env`；默认不扫 `run/` |
| skill 双份不一致 | M5 hash 校验或构建时从 resources 复制 |

## 12. 完成定义（整计划）

同时满足：

1. 可在本机仅启动 harness + 配置 LLM Key，完成多轮记忆相关对话调试；  
2. 记忆 JSON 与游戏内格式互导，preview/context 与 Java 权威实现 golden 一致；  
3. Web 可调 VirtualMaid 与 MemoryConfig 等价项，并查看完整 prompt/tool trace；  
4. `required` 场景结构断言可作为改 skill/tool 文案后的回归门禁；  
5. `tools/memory-harness/README.md` 足以让作者按步骤启动，无需再读本计划全文。
